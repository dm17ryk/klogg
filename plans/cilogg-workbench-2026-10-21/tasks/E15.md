# E15 — Plugin repositories with private Azure DevOps sign-in and update checks

**Read first:** [plugin repositories and configuration packs design](../../../docs/plugin-repositories.md),
[plugin SDK](../../../docs/plugin-sdk.md), the shared contracts in [08-ecosystem.md](../08-ecosystem.md)
and [decision D16](../../../docs/workbench/decisions.md).

**Integrated hard dependencies:** G01. Decision D16 records the design as proposed on 2026-11-17;
implementation starts only after the user approves it, and the approval also decides whether E15 may
run ahead of G02/G03 as E13a and R06 did. E16 and E09 depend on E15 (E09 through E16); R04 depends on
E15.

**Outcome:** the Plugins window manages several plugin catalogs (`plugins.json`, schema 1). A
repository signs in with none or with Azure DevOps, through the Git Credential Manager Git already
uses or a personal access token kept in the operating system credential store. Browse Plugins shows
one merged list with each entry's source; a plugin updates only from the repository it was installed
from. CILogg checks for updates silently at startup and once a day; installing stays a user action
unless auto-update is turned on for that repository. Nothing organization-specific is built in.

**Files and ownership:** `src/plugins/` (`pluginmanager.*`; new `pluginrepositories.*` for the
repository list, migration and source records; new `repositorycredentials.*` for the credential
manager and PAT store; new `pluginupdatechecker.*`), `src/ui/src/pluginuicontroller.cpp` (Repositories
dialog, merged Browse list, Source column, Update buttons and notices), the Commander/CLI/MCP command
tables for `plugin_manage`, `scripts/plugins/build_catalog.py` (generalized from
`package_examples.py`), `docs/plugin-sdk.md`, `docs/plugin-repositories.md`, tests in
`tests/unit/plugins_test.cpp`, a new `tests/ui/workbench_e15_test.cpp` and `tests/plugins/`.
QtKeychain becomes a dependency if open decision 4 of the design is accepted.

**Slices:**

- **E15a:** repository records in the plugin `settings.ini` (unique IDs that are never reused, an
  address that cannot be edited), migration of `catalogUrl` to the `default` repository, the merged
  catalog with per-repository results, an invalid entry failing only itself, `entry_id` covering
  the repository, install-source records and pinning with an explicit source switch
  (`switch_source`), the staged package's `kind` checked against its entry and never changed by an
  update, one Semantic Versioning 2.0.0 order for validation and update selection, the catalog keys
  `kind` (unsupported kinds hidden),
  `os: any`, `arch: any`, `min_host_version`, `released`, `homepage` and `license`,
  `build_catalog.py`, the `get_plugins` fields `kind` and `source`, and the operations
  `repositories`, `repository_add`, `repository_update`, `repository_remove` and `catalog` with
  `repository` through Commander, CLI, native MCP and Python.
- **E15b:** Azure DevOps sign-in: address forms (`visualstudio.com` converted to `dev.azure.com`)
  and Items API addresses; Git run by absolute path with `-c core.askPass=`, `GIT_TERMINAL_PROMPT=0`
  and no askpass variables; `git credential fill/approve/reject` with `capability[]=authtype` and the
  complete `fill` output, reject only after an in-scope 401 in a GUI operation; Bearer for Entra
  tokens and Basic otherwise; the PAT store, cleared when its repository is removed;
  `X-TFS-FedAuthRedirect: Suppress`; the normalized
  credential scope and `ManualRedirectPolicy` handling; a request `origin` set by each transport;
  `repository_sign_in` / `repository_sign_out`; and the input rules (no token arguments, no PAT and
  no prompt from MCP, Python or scenarios).
- **E15c:** silent update check after startup and every 24 hours (not in automation or headless
  mode), Updates entry and notices, Skip this version, per-repository auto-update within the
  installed major version, `check_updates` and the `get_plugins` `update` field.

**Interfaces (proposed additions):**

- `PluginRepositories::list() / add(...) / update(...) / remove(id)`; records `id`, `name`, `url`,
  `branch`, `path`, `signIn`, `credentialSource`, `enabled`, `autoUpdate`, `lastCheck`, `lastError`.
- `RepositoryCredentials::acquire(repository, interactive) -> Credential` (a type that keeps the
  token out of logs and clears it when destroyed), `approve(...)`, `reject(...)`, `storePat(...)`,
  `forget(...)`.
- `PluginManager::fetch(url, jobId, sha256, version, repository)` attaches a credential only inside
  the repository's scope.
- `plugin_manage` operations `repositories`, `repository_add`, `repository_update`,
  `repository_remove`, `repository_sign_in`, `repository_sign_out`, `check_updates`; `catalog`
  accepts `repository` and keeps the `url` option; `install` and `update` accept `switch_source`.
- `CommanderRequest::origin` (`gui`, `cli`, `mcp`, `python`, `scenario`), set by the transport only.
- `repository_update` edits only `name`, `enabled`, `auto_update` and `credential_source`;
  `repository_remove` also deletes the stored PAT.

**Coordination:** R06b crash dumps are memory images that can hold a token in use at the time of a
crash; the R06 card keeps them out of the shareable report zip unless the user adds them.

**Implementation steps:**

- [ ] Write failing Catch2 cases tagged `[plugins]` and `[workbench][E15]` for the behaviour in
  section 8 of the design, with a local HTTPS test server that records request headers and a fake
  `git credential` helper and credential store; confirm that they fail before the change.
- [ ] Implement E15a, pass its cases and the existing `[plugins]` and `tests/plugins` suites, review
  the diff and deliver it as a focused PR.
- [ ] Implement E15b with the credential cases (normalized scope, redirects, 203 and HTML replies,
  the Git environment, approve and reject calls, request origin, absence from settings, logs, the
  journal, job results and problem reports) and deliver it as a focused PR.
- [ ] Implement E15c with the update-check cases (deadline, automation skip, notices, auto-update
  within a major version, running plugin replaced when it stops) and deliver it as a focused PR.
- [ ] Verify each slice through GUI, CLI, native MCP and Python, build with the existing Windows build
  script, run the complete unit and integration suites, and record evidence and limitations in
  PROGRESS.json.

**Acceptance:** a user adds a private Azure DevOps repository by pasting its address, is signed in
through the credential manager they use for Git (or a PAT), sees its plugins next to the public ones
with their source, installs one, and gets a notice when a new version is published; the credential
never leaves its scope and appears in no file, log, journal, result or report; an older CILogg keeps
working with the same plugin folder.

**Rollback:** revert the slice PRs. The `repositories` settings are then unread, `catalogUrl` still
holds the address, and installed plugins keep working. A stored PAT stays in the credential store
under `CILogg plugin repository <id>` until the user deletes it.
