# E16 — Configuration packs: previews, decoders, actions, highlighters and filters as plugins

**Read first:** [plugin repositories and configuration packs design](../../../docs/plugin-repositories.md)
sections 3.3 and 4, [TShark/Lua message previews](../../../docs/workbench/tshark-preview.md),
[tasks/E15.md](E15.md) and [decision D16](../../../docs/workbench/decisions.md).

**Integrated hard dependencies:** E15 (packs install and update from plugin repositories, in the
same window as plugins). Decision D16 records the design as proposed on 2026-11-17; implementation
starts only after the user approves it. E09 depends on E16, so the later general packs extend this
pack format instead of duplicating it; R04 depends on E16. MD03 activates the packs' Python
decoders; that is a coordination note, not a hard edge.

**Outcome:** a configuration pack is a plugin package (`"kind": "config-pack"`) whose `content`
carries preview definitions in the format of `previews.json`, Lua decoders for TShark, Python
decoders, actions with automatic responses, highlighter sets and predefined filters, all in the
formats CILogg already imports and exports. Packs are versioned and installed, updated and removed
in the same Plugins and Packs window as plugins, from the same repositories or from a local zip; a
pack with one kind of content is listed as that kind (for example "Filters"). Pack items can be
edited in place: the installed version stays pristine as the merge base, the edits are an overlay in
the user's data, and an update is a three-way merge with a dialog for conflicts, never a silent
overwrite. Pack automatic responses start switched off, pack Lua is loaded by TShark as trusted
scripts while the pack is enabled, and **Export as Pack** turns the user's own items into a pack to
share through a public or private repository.

**Files and ownership:**

- `src/plugins/src/pluginmanifest.cpp` and `pluginmanager.cpp`: the pack kind, `content`
  validation, no process; the catalog key `contents`.
- A new `packedits.*` (the overlay in `pack-edits/<pack-id>/`, base hashes, tombstones, Reset to
  Pack Version) and `packmerge.*` (three-way merge of structured items by identity and field,
  identified arrays per element, diff3 for text and for ordered lists without identities, the
  staged apply that installs the new version and the rebased overlay in one step), and the merge
  dialog in `src/ui/`.
- Previews: `src/ui/src/previewrepository.cpp` and a new `previewpackregistry.*` (merged previews
  with the pack's name, pack blocks renamed to `<pack-id>/<block>`, precedence of user items,
  collisions between packs, the aggregate quotas of `PreviewService::definitions()`), the preview
  settings UI (edit in place, Copy to My Previews with the block closure, Packs…).
- TShark: the profile snapshot (pack Lua, edited or not, and routes merged at session start, never
  into the saved configuration; a generated loader that runs each pack's files in its own Lua
  environment; the profile limit raised from 8 to 32 in `tsharkpreviewclient.cpp`,
  `scripts/plugins/message_decoder_preview_worker.py` and `scripts/plugins/message_decoder_pdu.py`;
  the route limits; sessions discarded on change).
- Actions, highlighters and filters: the action repository and Actions window, the highlighter set
  collection and dialog, the predefined filters collection and list (pack items with the pack's
  name, edit in place, Copy to My ..., identity and precedence, collisions, merged limits, Packs…),
  automatic responses from packs off until enabled; on or off and active sets kept as user state
  per pack and item.
- `src/ui/src/configurationexport.cpp`: live and snapshot exports of the user's own items only.
- Export as Pack: the dialog and `pack_export`.
- The Plugins and Packs window (kind, local-edit state, "Update needs a merge", Reset to Pack
  Version, Export as Pack…, "Needs TShark"), `docs/plugin-sdk.md`,
  `docs/workbench/tshark-preview.md`, `DOCUMENTATION.md` (the guide), an example pack under
  `plugins/examples/`, tests in `tests/unit/plugins_test.cpp`, `tests/unit/previewdecoder_test.cpp`,
  a new `tests/unit/packmerge_test.cpp` and a new `tests/ui/workbench_e16_test.cpp`.

**Slices:**

- **E16a:** the pack kind and `content` validation, JSON previews and Lua for TShark, `decoder_routes`,
  the public example pack, pack fields in `get_plugins`, the install, enable and update confirmations
  that say a pack's Lua runs as local code with the user's permissions; local edits as an overlay,
  the three-way merge engine (structured items and diff3 text), the merge dialog, Reset to Pack
  Version and the automation strategies, for previews, blocks and Lua or Python files.
- **E16b:** Python decoders run through the MD03 decoder contract. Until MD03 exists, E16a installs,
  updates and merges them with the pack and lists them as requiring a newer CILogg.
- **E16c:** actions with automatic responses (off until the user enables them), highlighter sets
  and predefined filters from packs, their local edits and merge, and the Packs… buttons in the
  Actions, Highlighters and filters windows.
- **E16d:** Export as Pack (dialog and `pack_export`) and its part of the in-app guide.

**Interfaces (proposed additions):** manifest keys `kind`, `pack_format` and `content` with
`previews`, `actions`, `highlights`, `filters`, `lua` (`folder`, `load`), `decoder_routes` and
`python_decoders`; catalog key `contents`; `PreviewPackRegistry::previews()` and `luaProfile()`;
`PackEdits::edited(item) / reset(item) / overlay(pack)`; `PackMerge::merge(base, theirs, mine) ->
{result, conflicts}`; `plugin_manage` operations `pack_edits`, `pack_reset`, `pack_export` and the
`update` option `strategy` (`fail`, `keep_mine`, `take_theirs`); the `get_plugins` fields `kind`,
`contents`, `localEdits` and, for packs, counts of `previews`, `actions`, `responses`,
`highlighterSets`, `filters`, `luaFiles` and `pythonDecoders`.

**Implementation steps:**

- [ ] Write failing cases tagged `[plugins]`, `[previewdecoder]`, `[packmerge]` and `[workbench][E16]`:
  pack manifest validation (`kind` read first, no process keys at the top level including `actions`
  and `configuration`, `protocol_version: 1`, every Lua file listed, at most 8 files of 1 MiB inside
  the folder, preview routes naming only pack previews), process operations rejected for packs,
  pack previews with the pack's name, Copy to My Previews with the block closure and renamed
  colliding blocks, pack blocks resolved only inside their pack, user precedence, a preview-name
  collision between packs refused, the aggregate preview quotas, exports and project snapshots
  without pack items, pack Lua in the profile snapshot only while enabled (copied, hashed in
  `scriptSha256`, loaded in the listed order, never written into the saved configuration, one
  environment per pack so two packs with the same global keep their own values), the 32-file and
  route limits, sessions discarded on enable, disable and update, JSON fallback without TShark,
  inactive `python_decoders`.
- [ ] Write failing merge cases: the installed folder unchanged by edits; overlay base hashes and
  tombstones; Reset to Pack Version; every three-way case per item (not edited, edited only
  locally, different fields, the same field, deleted against changed, added, removed) with the same
  new value on both sides not a conflict; identified arrays merged per element; diff3 for Lua and
  Python files and highlighter rules, with and without conflicts; Keep Mine, Take Theirs, Edit,

  edits; strategies `fail`, `keep_mine` and `take_theirs` and no dialog outside the GUI; auto-update

- [ ] Implement E16a in the owned files, add the public example pack (synthetic protocol, no private
  Lua or configuration), and pass the new cases plus the existing preview, TShark and plugin suites.
- [ ] Write failing cases for E16c (pack actions, responses, highlighters and filters with the pack's
  name, edit in place and merge, identities and namespacing, Copy to My ..., user precedence,

- [ ] Write failing cases for E16d (the selected items with the blocks they need, edited pack items

- [ ] Verify install, update with and without a merge, enable, disable, remove and export through
  GUI, CLI, native MCP and Python, build with the existing Windows build script, run the complete
  suites, record evidence and limitations in PROGRESS.json and deliver each slice as a focused PR.
- [ ] E16b in its own PR once MD03's decoder contract is merged.

**Acceptance:** a pack installed from a repository adds its previews, actions, highlighters and
filters (shown with the pack's name) and lets TShark decode with its Lua without per-file approval;
none of its automatic responses sends anything until the user turns it on. The user edits a pack
filter and a pack Lua file, a new pack version changes other items and one of the same: the update
keeps the untouched edits, takes the new items, and shows the conflict in the merge dialog; Cancel
keeps the old version, Apply installs the new one with the chosen result. From automation the same
update refuses with the conflict list unless a strategy is given. Export as Pack of a few items
produces a pack that installs on another computer. Previews still fall back to JSON when TShark is
not configured.

**Rollback:** revert the PRs. Installed packs are then listed as invalid plugins and nothing loads
them; the `pack-edits` folder is left unread; the user's own previews, actions, highlighters,
filters and decoder settings are unchanged.
