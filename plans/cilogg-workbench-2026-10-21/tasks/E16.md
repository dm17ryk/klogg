# E16 — Configuration packs: previews, decoders, actions, highlighters and filters as plugins

**Read first:** [plugin repositories and configuration packs design](../../../docs/plugin-repositories.md)
section 4, [TShark/Lua message previews](../../../docs/workbench/tshark-preview.md),
[tasks/E15.md](E15.md) and [decision D16](../../../docs/workbench/decisions.md).

**Integrated hard dependencies:** E15 (packs install and update from plugin repositories). Decision
D16 records the design as proposed on 2026-11-17; implementation starts only after the user approves
it. E09 depends on E16, so the later general packs extend this pack format instead of duplicating
it; R04 depends on E16. MD03 activates the packs' Python decoders; that is a coordination note, not a
hard edge.

**Outcome:** a configuration pack is a plugin package (`"kind": "config-pack"`) whose `content`
carries preview definitions in the format of `previews.json`, Lua decoders for TShark, Python
decoders, actions with automatic responses, highlighter sets and predefined filters, all in the
formats CILogg already imports and exports. Packs are versioned, installed, updated, enabled and
removed like plugins, from the same repositories or from a local zip. Their items are read-only
(Copy to My ... makes an editable copy), their automatic responses start switched off, and their Lua
is loaded by TShark as trusted scripts while the pack is enabled, because installing it from a
repository the user added is the trust decision. A team's private configuration and protocol Lua
are delivered from a private repository instead of being published.

**Files and ownership:**

- `src/plugins/src/pluginmanifest.cpp` and `pluginmanager.cpp`: the pack kind, `content`
  validation, no process.
- Previews: `src/ui/src/previewrepository.cpp` and a new `previewpackregistry.*` (merged read-only
  previews, pack blocks renamed to `<pack-id>/<block>`, precedence of user copies, collisions between
  packs, the aggregate quotas of `PreviewService::definitions()`), the preview settings UI (lock,
  pack name, Copy to My Previews with the block closure).
- TShark: the profile snapshot (pack Lua and routes merged at session start, never into the saved
  configuration; a generated loader that runs each pack's files in its own Lua environment; the
  profile limit raised from 8 to 32 in `tsharkpreviewclient.cpp`,
  `scripts/plugins/message_decoder_preview_worker.py` and `scripts/plugins/message_decoder_pdu.py`;
  the route limits; sessions discarded on change).
- Actions, highlighters and filters: the action repository and Actions window, the highlighter set
  collection and dialog, the predefined filters collection and list (pack items read-only with a
  lock, Copy to My ..., precedence, collisions, merged limits), automatic responses from packs off
  until enabled, with the choice kept per pack and response name.
- `src/ui/src/configurationexport.cpp`: live and snapshot exports of the user's items only.
- The Plugins window (kind, "Needs TShark"), `docs/plugin-sdk.md`,
  `docs/workbench/tshark-preview.md`, an example pack under `plugins/examples/`, tests in
  `tests/unit/plugins_test.cpp`, `tests/unit/previewdecoder_test.cpp` and a new
  `tests/ui/workbench_e16_test.cpp`.

**Slices:**

- **E16a:** the pack kind and `content` validation, JSON previews and Lua for TShark, read-only
  previews with Copy to My Previews, `decoder_routes`, the public example pack, pack fields in
  `get_plugins`, and install, enable and update confirmations that say a pack's Lua runs as local
  code with the user's permissions.
- **E16b:** Python decoders run through the MD03 decoder contract. Until MD03 exists, E16a installs
  and updates them with the pack and lists them as requiring a newer CILogg.
- **E16c:** actions with automatic responses (off until the user enables them), highlighter sets
  and predefined filters from packs.

**Interfaces (proposed additions):** manifest keys `kind`, `pack_format` and `content` with
`previews`, `actions`, `highlights`, `filters`, `lua` (`folder`, `load`), `decoder_routes` and
`python_decoders`; `PreviewPackRegistry::previews()` and `luaProfile()`; the `get_plugins` field
`kind` and, for packs, counts of `previews`, `actions`, `responses`, `highlighterSets`, `filters`,
`luaFiles` and `pythonDecoders`.

**Implementation steps:**

- [ ] Write failing cases tagged `[plugins]`, `[previewdecoder]` and `[workbench][E16]`: pack
  manifest validation (`kind` read first, no process keys at the top level including `actions` and
  `configuration`, `protocol_version: 1`, every Lua file listed, at most 8 files of 1 MiB inside the
  folder, preview routes naming only pack previews), process operations rejected for packs,
  read-only previews, Copy to My Previews with the block closure and renamed colliding blocks
  (unchanged after the pack is updated or removed), pack blocks resolved only inside their pack,
  user precedence, a preview-name collision between packs refused, the aggregate preview quotas,
  exports and project snapshots without pack items, pack Lua in the profile snapshot only while
  enabled (copied, hashed in `scriptSha256`, loaded in the listed order, never written into the
  saved configuration, one environment per pack so two packs with the same global keep their own
  values), the 32-file and route limits, sessions discarded on enable, disable and update, JSON
  fallback without TShark, and inactive `python_decoders`.
- [ ] Implement E16a in the owned files, add the public example pack (synthetic protocol, no private
  Lua or configuration), and pass the new cases plus the existing preview, TShark and plugin suites.
- [ ] Write failing cases for E16c (pack actions, highlighters and filters read-only with Copy to
  My ..., user precedence, collisions between packs refused, merged store limits, pack automatic
  responses off after install and their on or off choice kept across an update), then implement it.
- [ ] Verify install, update, enable and disable of a pack through GUI, CLI, native MCP and Python,
  build with the existing Windows build script, run the complete suites, record evidence and
  limitations in PROGRESS.json and deliver each slice as a focused PR.
- [ ] E16b in its own PR once MD03's decoder contract is merged.

**Acceptance:** installing a pack from a repository adds its previews, actions, highlighters and
filters (read-only) and lets TShark decode with its Lua without per-file approval; none of its
automatic responses sends anything until the user turns it on; updating the pack changes its items
and the next decode uses the new Lua; disabling it removes them; the user's own items and copies are
never changed by a pack; previews still fall back to JSON when TShark is not configured.

**Rollback:** revert the PRs. Installed packs are then listed as invalid plugins and nothing loads
them; the user's previews, actions, highlighters, filters and decoder settings are unchanged.
