# R05 — Make the in-app update hand-off and scheduled checks robust

**Read first:** [product specification](../00-product-spec.md), [execution guide](../MASTER_GUIDE.md),
and the shared contracts in [09-release.md](../09-release.md). Execute only this task or its recorded,
independently reviewable slice.

**Integrated hard dependencies:** G01. Under decision
[D12](../../../docs/workbench/decisions.md) the user authorized this fix ahead of G02/G03 completion
on 2026-11-13, so G02/G03 are not hard edges of R05; it uses the existing Windows build script and
unit suites as they are. R04 depends on R05.

**Outcome:** An update downloaded with "install on exit" is installed exactly once by the
installation that downloaded it, never re-run for a version that is already installed, and a failed,
declined or abandoned install is explained once at the next start. A scheduled update check that
cannot reach GitHub never interrupts the user; it is retried quietly.

**Reported symptoms (2026-11-13, release continuous-26.04.2.1203, Windows):**

- After downloading an update and closing CILogg, a Windows dialog titled with the path of the
  downloaded `cilogg-*-setup.exe` sometimes said "The specified path does not exist."
- On startup a dialog sometimes said the update server could not be reached.

**Root cause (from the updater code and the user's update cache):**

- Every `cilogg.exe` process constructed `VersionChecker`, including the `cilogg.exe command ...`
  process the MCP server starts for each tool call, secondary instances and development builds named
  `cilogg.exe` that share `%LOCALAPPDATA%\cilogg\updates`. Construction loaded
  `pending-update.json`, hashed the 26 MB package while holding the file open (Qt opens files without
  delete sharing, so the updated CILogg could not remove it) and armed the exit-time install.
- The transaction was never consumed, so later exits ran the installer again; the user's
  1203 cache still holds a scheduled record for the already installed version.
- The helper called `ShellExecuteExW("runas")` without `SEE_MASK_FLAG_NO_UI`, so the shell showed its
  own error box when the launch failed; the helper then logged exit code 1223.
- Every failure of the scheduled check went to the same modal error dialog as a manual check.

**Files and ownership:** `src/versioncheck/` (updater controller, transaction files and helper
protocol), `src/updater/main.cpp` (helper), `src/ui/src/updateuicontroller.cpp`,
`src/app/kloggapp.h`, `src/app/cli.h` and `src/app/main.cpp` (the startup acknowledgement, written
before session restore), `tests/unit/versionchecker_test.cpp`.

**Interfaces and transaction states (design implemented on
[PR #105](https://github.com/dm17ryk/klogg/pull/105)):**

- `VersionChecker` construction is passive; `activate()` (primary GUI process only, not in
  automation/headless mode) acknowledges an updated start, reconciles the persisted transaction by
  installation path and version, and arms the exit-time install.
- **Claim.** At exit, `pending-update.json` is claimed by one atomic, non-replacing rename to
  `pending-update.launched.json`. If a launched record already exists the claim fails as busy and
  nothing is launched. After the rename the claimed record is re-read and its token compared with the
  token this process validated; on a mismatch the record is renamed back (non-replacing) and nothing
  is launched. The launched record carries `launchedAt` (UTC) with the token, version, installation
  path, mode, `packagePath` and `stagedPath`.
- **Helper.** The helper holds an exclusive `updater.lock` in the updates directory for its whole
  lifetime. It uses a native path, `SEE_MASK_FLAG_NO_UI`, checks that the package exists and retries
  transient launch errors (not a declined UAC prompt). For setup installs `stagedPath` must equal
  `packagePath`, and the helper verifies the SHA-256 of the exact file it launches. It writes
  `install-result.txt` (`token`, `mode`, `phase`, `code`); `relaunch` is a distinct phase, so a
  completed install whose relaunch failed is not reported as a failed install.
- **Startup acknowledgement.** An updated start writes the acknowledgement early in startup, before
  session restore, so the helper's 30 s acknowledgement window is met even with a large session.
- **Next start (reconciliation of `pending-update.launched.json`).** Reconciliation first consumes
  the launched record atomically by renaming it to `pending-update.reconciling.json`; only the process
  that wins that rename reports, so a report is never shown twice. Then:

  | State at the next primary start | Result |
  |---|---|
  | `updater.lock` is held | The helper is running: keep the launched record, report nothing. |
  | `install-result.txt` with the record's token exists | Report the outcome once; when the running version equals the record's version the transaction is complete and is cleared. |
  | No result, `launchedAt` younger than 2 minutes | The helper may still be starting: keep the record. |
  | No result, `launchedAt` 2 minutes or older, lock free | Abandoned claim (the process exited, `startDetached` failed, or the helper died before writing a result): report it once and restore the package as ready to install, not re-armed. |

- **Ownership of shared files.** Cleanup never deletes a package referenced by any persisted record
  (pending, launched or reconciling) of any installation. A pending record that belongs to another
  installation path is never overwritten.
- Signals `installFailed(message)` and `backgroundCheckFailed(message, willRetry)`; `errorOccurred`
  is reserved for user-initiated operations.

**Implementation steps:**

- [ ] Write Catch2 cases tagged `[updater]` in `tests/unit/versionchecker_test.cpp` for passive
  construction, activation, completed and foreign transactions, the non-replacing claim (busy when a
  launched record exists), the token re-check after the claim, a held `updater.lock` kept as running,
  a young claim kept, an abandoned claim reported once and restored as ready without re-arming, a
  launched record consumed once by two concurrent starts, cleanup keeping every referenced package, a
  foreign pending record never overwritten, `stagedPath == packagePath` for setup installs, the
  helper's hash check of the launched file, the `relaunch` phase, the helper launch policy, and
  silent retried background checks against a local server.
- [ ] Build with the existing Windows build script, run `cilogg_tests.exe "[updater]"`, and confirm
  the new cases fail on the unfixed code.
- [ ] Implement the interfaces and transaction states above in the owned files.
- [ ] Rebuild, pass the focused and complete unit suites, review the diff, and record evidence and
  limitations in PROGRESS.json. Deliver as a focused PR with green hosted CI.

**Acceptance:** Exactly one process can hand a transaction to the helper; CLI and secondary
processes never read or lock it; an installed version is never reinstalled; a failed or abandoned
install is reported exactly once and leaves the package ready but not armed; a claim is never left
stranded; scheduled-check failures show no dialog and are retried.

**Rollback:** Revert the PR. Persisted `pending-update.json` files stay readable by the previous
code; `pending-update.launched.json`, `pending-update.reconciling.json` and `updater.lock` left
behind are ignored by it.
