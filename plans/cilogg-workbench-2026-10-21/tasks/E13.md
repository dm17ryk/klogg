# E13 — Add interactive plugin views

**Read first:** [product specification](../00-product-spec.md), [execution guide](../MASTER_GUIDE.md),
the shared contracts in [08-ecosystem.md](../08-ecosystem.md), and the
[plugin views design](../../../docs/plugin-views.md). Execute only this task or its recorded,
independently reviewable slice.

**Integrated hard dependencies:** G01, G02, G03. See decision
[D11](../../../docs/workbench/decisions.md): the user authorized slice E13a ahead of G02/G03
completion on 2026-11-11.

**Outcome:** Process plugins can build interactive views (fields, buttons, progress, large tables)
in every window kind CILogg uses: docks on any side or floating, top-level windows, modal or
modeless dialogs, and message boxes with an optional auto-close timeout. Views stay alive while the
user works, and their actions are callable from GUI, CLI and native MCP.

**Depends on:** G01–G03 (common prerequisites). E13 coordinates with E01: views announce
themselves through one `host_features` entry in `initialize`, which E01's negotiated capabilities
absorb later without changing the view messages.

**Files and ownership:**

- Modify existing `src/plugins/src/pluginmanifest.cpp`, `src/plugins/src/pluginprocess.cpp`,
  `src/plugins/src/pluginmanager.cpp` and their headers, `src/ui/src/pluginuicontroller.cpp`,
  `docs/plugin-sdk.md`, and the Python SDK.
- Create the view renderer under `src/ui/`, `plugins/examples/view-demo/`, and
  `docs/plugin-views.md`.
- Tests: `tests/ui/workbench_e13_test.cpp` and plugin unit cases in `tests/unit/plugins_test.cpp`,
  registered in the existing test CMakeLists; Python SDK cases under `tests/plugins/`.

**Interfaces (proposed additions):**

- Manifest `views`: `id`, `title`, `kind` (`dock`, `window`, `dialog`), `area` (`left`, `right`,
  `top`, `bottom`), `floating`, `width`, `height`, `modal`, `menu`.
- Notifications from host to plugin: `view/opened`, `view/closed`, `view/event`,
  `ui/message_result`.
- Notifications from plugin to host: `view/update` (a root or a patch), `view/show`, `view/hide`,
  `ui/message`, `ui/close_message`.
- Protocol version 1 is kept; plugins without views see byte-for-byte unchanged behaviour.
- View buttons start ordinary plugin jobs (`invoke_plugin`) with the current field values, so
  every view operation is also public through Commander and native MCP.
- Plugin process environment: `CILOGG_EXECUTABLE`, `CILOGG_INSTANCE_ID`.
- Job state `cancelling` (grace period of up to 10 s after `cancel_plugin_job`).
- `pause_comm --wait`.

**Required behavior:**

- Patches update widgets in place; scroll position, selection and typed field text survive updates.
- Bounded resources: 8 views per plugin, 512 elements per view, 50,000 table cells, the existing
  1 MiB message limit, renders coalesced to 10 per second. Unknown element types and properties are
  ignored with one diagnostic.
- Views keep process isolation: the plugin still sends notifications only, never host requests.
- Window close sends `view/closed`. A plugin restart re-sends `view/opened` for views still open.
  Removal or disable closes its docks.

**Acceptance:** A plugin view can be opened from the Plugins menu, driven by its plugin through
patches without losing user state, and its buttons run the same jobs that CLI and MCP can run.
Plugins without views behave exactly as before.

**Rollback:** Ignore the manifest `views` key and the `view/*` notifications. Existing actions,
panels and jobs keep working. The environment variables, `cancelling` and `pause_comm --wait` are
additive.
